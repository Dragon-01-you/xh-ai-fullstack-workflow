# 03 · 需求 / spec / 架构（Phase 4–5）

> 工具：**`grilling` / `grill-with-docs`**（访谈+术语/ADR）、**`to-spec`**（把对话综合成 spec）、**`codebase-design`**（模块/接口/seam 词汇）、**`prototype`**（设计问题纸上想不清时做一次性原型）。

## 一、先写闭环句（一句话）

格式：**谁 → 打开哪 → 做什么动作 → 看到什么结果 → 数据怎么变**

- ✅「访客打开 /collect，填姓名+邮箱提交 → 看到“已收到” → submissions 表多一条」
- ❌「做一个表单系统」（模块名）
- ❌「实现表单提交功能」（功能名）

## 二、spec 模板（一页纸）

```markdown
# SPEC · <切片名>

## 问题（用户视角）
谁、在什么场景、遇到什么麻烦、现在怎么凑合。

## 用户故事
- S1 作为 <角色>，我想 <行为>，这样 <好处>。
- S2 …

## 验收（可手工执行，含失败）
- [ ] S1 打开 <路径>，<操作> → 看到 <结果>；数据：<怎么变>
- [ ] S2 <操作> → 看到 <结果>
- [ ] S3（失败）<异常操作> → 看到 <提示>，不白屏、不 500

## 不做什么
- 范围排除：<这版不做…>
- 安全红线：<永远不做…，除非明确授权>

## 失败模式
- 输入错：
- 依赖挂：
- 重复/并发：

## 前置条件（来自扫描）
- 需要：<账号/支付/实名/域名/运行时>
- 已有：<…>；缺：<…>；怎么补：<…>

## 学习点（这版要学到的东西）
```

## 三、验收的三条标准

1. 不写内部细节（“接口返回 200”不算验收）；
2. 每条能在 5 分钟内手工做；
3. 预期具体到“看到什么 / 数据变成什么”，至少一条失败路径。

> **验收写不出来 = 需求没想清，不许写代码。**

## 四、架构模板（一页图）

```markdown
# ARCHITECTURE · v0

## 1. 数据流
[浏览器] → [路由/接口] → [业务] → [存储] → 返回 → [页面]

## 2. 模块清单
| 模块 | 职责（一句话） | 对外接口 | 不负责什么 |

## 3. 接口契约
| 接口 | 输入 | 输出 | 错误 | 对应验收 |

## 4. 数据模型
| 表 | 字段 | 类型 | 约束 | 为什么 |

## 5. 测试 seam
| seam | 类型 | 覆盖 | 抓什么 | 漏什么 |

## 6. 部署拓扑
- 运行环境 / 入口 / 环境变量键 / 数据在哪 / 日志看哪

## 7. 未解问题（诚实清单）
```

## 五、ADR（每个取舍三行）

```markdown
# 决策：<一句话>
选项：A / B / C（各带代价）
我选：B
理由：<一行>
什么情况下我会改选：<一行>
```

**闸门**：能指着架构图讲清数据从哪来、到哪去、哪一层最容易坏。
